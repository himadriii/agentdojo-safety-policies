# A Supervised Risk Policy for Approving LLM-Agent Tool Calls under a Reviewer Budget

## Abstract

Language-model agents that call tools can be hijacked by instructions hidden in the data they read, an attack known as indirect prompt injection. A common defence places an approval policy in front of every tool call, which approves the call, denies it, or escalates it to a reviewer, with each task allowed only a small number of escalations. This report describes and evaluates one such policy, built as a supervised classifier. A random forest scores each proposed call from the visible context alone, using 39 features that describe the tool, whether the call's arguments are grounded in the user's request, and whether instruction-like text has appeared in earlier tool output. Two calibrated thresholds turn the score into a decision. The training data were constructed without running an agent, by replaying the benchmark's ground-truth calls with attack text planted in the environment. Offline, on held-out tasks, the classifier separated unsafe from safe calls almost perfectly, with an AUROC of 0.997, 99.5% of unsafe calls flagged and 4.8% of safe calls flagged. In real agent runs on the same suite, the policy blocked every attack when it could not escalate, with no attack succeeding in ten pairs against six of ten with no policy, but once an escalation budget was available most attacks returned, because the only reviewer used approved every request. On three further suites the policy generalized only partly: it blocked the attacker's transfers, messages and hotel reservations, but it also blocked some legitimate messages and payments, and in the Slack suite it missed an attack that is itself a read-only web request. On the group's shared held-out splits over the same three suites, run once after the policy was frozen, no attack succeeded in Slack or travel, but five of eighteen banking attacks succeeded, every one a password change that the policy approved. We conclude that a context-feature classifier is cheap and effective inside the suite it was trained on, but needs multi-suite training data, tool metadata and a capable reviewer before it can be relied upon. All real-run samples are small, so these findings are indicative rather than conclusive.

## 1 Introduction

Tool-using language-model agents read emails, files, web pages and chat messages and then act on what they read, by sending mail, moving money or deleting files. Because an agent cannot reliably tell the user's instructions from instructions embedded in that data, an attacker who controls a document can steer the agent into harmful actions (Greshake et al., 2023). AgentDojo (Debenedetti et al., 2024) provides a benchmark for measuring this, with user tasks, injection tasks and attack templates across four suites: workspace, travel, banking and Slack.

Approval policies are one response to this problem. Asking a person to confirm every action defeats the purpose of having an agent, while approving everything is unsafe. A policy that decides call by call whether to approve, deny or escalate lets a small reviewer budget be spent where it matters most. Two quantities summarize the trade-off. The task completion rate (TCR) is the share of tasks that finish correctly without the attack succeeding, and the human-in-the-loop load is the number of reviewer calls spent.

Our group implemented several policies behind one shared interface, and this report covers the third, a supervised risk model. The research question is whether a classifier trained offline on labeled tool calls, using only the visible context, can decide which calls to approve, deny or escalate well enough to keep tasks completing safely under a small reviewer budget, and whether it carries over to suites and attacks it has not seen.

## 2 Method and novelty

The policy implements the group's shared interface, in which it receives the user's task, the proposed call, the conversation so far, a read-only view of the environment, the remaining budget and some metadata, and returns a decision with an optional reason and score. Benchmark labels, injection task identifiers, injection goals and attack names are never available to it. It makes no calls to a language model, so it adds no tokens to a run.

Each proposed call is converted into 39 numbers drawn from five groups. The first describes the type of tool, whether it only reads, sends or shares something outside the account, moves money, deletes, or otherwise writes. The second measures grounding, meaning whether the recipient addresses and argument words appear in the user's task, in the contact list, in ordinary tool output, or only in text that looks like an instruction. The third looks for injection-like text in earlier tool output, using generic cue phrases such as "ignore previous instructions", "before you can solve the task" or `<INFORMATION>` blocks, and isolates the instruction-like span so that the model can ask whether the call's arguments come from it. The fourth asks whether the task even mentions the action, such as sending, deleting or sharing. The fifth counts sensitive keywords that do not appear in the task. Raw words, such as the attacker's address, are deliberately not features, so that the model cannot simply memorize the benchmark.

The training data were built without running an agent. For every combination of user task, injection task and attack style, we load an AgentDojo environment containing the attack text, replay the user task's ground-truth calls with the benchmark's own replayer, and splice the injection task's calls in right after the tool result that carried the text. Calls from the user task are labeled safe and calls from the injection task unsafe, and these labels exist only in the dataset. Two choices matter here. Safe calls also appear inside attacked conversations, so the mere presence of injected text is not a shortcut for the model. A variant with no injection text places the attacker's calls in clean conversations, so the model also learns plain mismatch with the task. We used seven attack styles, three of which appear only in the evaluation data. The benchmark supplies attacker calls only for the first six injection tasks, so we wrote the sequences for the remaining eight by hand from the task goals, which is an assumption.

We compared logistic regression, histogram gradient boosting and a random forest (Breiman, 2001) using cross-validation grouped by task, chose the random forest, and calibrated its scores with Platt scaling (Platt, 1999), using scikit-learn (Pedregosa et al., 2011). A call is approved below a risk of 0.25, escalated from 0.25 to 0.90, and denied at 0.90 or above. The escalation threshold is the lowest score that flags at most 3% of safe development calls, with a floor of 0.25 because the scores of safe calls saturate near zero.

The contribution lies less in the classifier than in how it is built and audited. It combines labeled contexts constructed from ground truth with planted attack text, which costs no model tokens, features that test whether a call's arguments come from the user's request or from injected text, and task-level splits that keep both user tasks and injection tasks apart, with some attack styles held out entirely. It also reports two audit findings openly. Features describing a call's position in the conversation leaked the place where we splice in the attack, and were removed. Labeling the read-only calls of an attack chain as unsafe taught the model that a call with no arguments is dangerous, which flagged 23% of real safe actions until we stopped labeling reads as unsafe, after which the figure was one in seventy.

## 3 Evaluation

The dataset contains 9,608 labeled calls from the workspace suite, of which 7,324 are used for development, covering 28 user tasks and 10 injection tasks, and 2,284 are held out, covering 12 user tasks and 4 injection tasks, with pairs that mix the two groups dropped. After removing the read-only calls of attack chains, 1,956 held-out calls remain, of which 644 are safe and 1,312 unsafe. The model, features and thresholds were fixed on development data before the held-out data were used, and the offline held-out evaluation was run once.

We ran six kinds of experiment. The first was cross-validation on the development data, grouped by user task and by injection task. The second was an offline evaluation on the held-out calls, reporting the area under the ROC and precision-recall curves, the share of unsafe calls flagged and the share of safe calls flagged or denied, including for the three attack styles never seen in training. The third was an offline replay with an escalation budget, a proxy for the runner's own metrics in which the simulated agent always follows the injection, a denied safe call fails the task, and an attack succeeds only if every one of its unsafe calls runs. In this replay a perfect reviewer approves safe calls and denies unsafe ones, while a naive reviewer approves everything. The fourth was a set of real runs in the workspace suite on the held-out tasks, using the shared AgentDojo runner with gpt-oss-20b (OpenAI, 2025) as the agent and a mock reviewer that approves every escalation. There were six stages over twelve user tasks, giving 72 run slots: the policy at budgets of 0, 2 and 5 with the important-instructions attack, the policy and the approve-everything baseline without an attack, and the baseline with the attack. Only the injection task that creates an attacker's calendar invite fit within the free-tier limits of the hosting service. The fifth was a set of real runs on the banking, Slack and travel suites, using the group's shared development splits, with the policy at a budget of two, gpt-oss-20b as both agent and language-model reviewer, served through LM Studio. The sixth was the group's shared held-out run on the same three suites, performed once after the policy was frozen, at budgets of 0, 1, 2, 3 and 5, with the same agent and reviewer and one run per user and injection task pair.

We judged the first two experiments by discrimination and flag rates, and the last three by completion rate, attack success, task completion and reviewer calls. The offline baselines are approve-everything and escalate-everything, and approve-everything is the baseline for the real workspace runs. The group's shared baseline runs for the other three suites were not available to us, so there is no utility baseline for the fifth experiment.

## 4 Results and discussion

On development data, cross-validated AUROC ranged from 0.985 to 0.998 for logistic regression, from 0.997 to 0.9998 for gradient boosting and from 0.998 to 1.000 for the random forest, depending on whether folds were grouped by user task or by injection task. On the held-out calls, the random forest reached an AUROC of 0.997 and an AUPRC of 0.999, flagged 99.5% of unsafe calls and denied 97.6% of them outright. It flagged 4.8% of safe calls and denied 3.3%. Results for the three attack styles never seen in training were almost identical, with 99.3% of unsafe calls flagged, so the model is not merely memorizing attack wording. The wrongly denied safe calls were all one legitimate file deletion in a single user task, repeated across seven attack variants, and the seven missed unsafe calls were all the attacker's calendar invite, which resembles the meetings users genuinely create.

In the offline replay with a budget of two and a perfect reviewer, the policy completed 91.7% of tasks safely with an attack success rate of 2.1% and 30 reviewer calls, whereas approving everything completed 2.4% with 97.2% of attacks succeeding, and escalating everything completed 48.8% with 320 reviewer calls. With a reviewer that approved everything, safe completion fell to 86.0% and attack success rose to 9.7%. These are simulated and probably optimistic figures, but they indicate that the policy removes nearly all attacks while spending an order of magnitude fewer reviewer calls than escalating everything.

The real workspace runs were less favourable. Of 72 planned run slots, 64 finished and eight were skipped because a single request exceeded the hosting service's per-minute token limit. Considering the ten user tasks that every configuration finished, approving everything completed two tasks safely and let the attack succeed six times. The policy with a budget of zero completed four tasks safely and let the attack succeed in none of the ten pairs. With a budget of two it completed two tasks safely and the attack succeeded five times, and with a budget of five it completed three and the attack succeeded twice. Without an attack the policy completed nine of ten tasks, flagging two of 22 actions and blocking one, the same completion as approving everything. The pattern follows from how escalation works. With no budget, an escalation is denied automatically, so only the policy's own judgment counts and every attack was blocked. With a budget, the policy still flagged the attacker's invite, but its score was 0.62 to 0.89 in five runs, so it was escalated, and 0.90 to 0.95 in three runs, so it was denied. The escalated calls went to a mock reviewer that approved them, which is why five attacks ran at a budget of two. The safety of escalated calls therefore depends entirely on the reviewer, which we could not test with a capable one in this suite. We did not lower the denial threshold after seeing this, because the held-out data must not be used for tuning. With about ten pairs per setting a difference of one run is noise, and the agent itself completes only two of ten tasks when nothing is blocked, so utility is largely limited by the agent rather than the policy.

On the other suites the policy generalized partly. In banking all 18 development pairs finished, with nine tasks completed and no attack succeeding. The policy denied 21 calls, of which 18 sent money to the attacker's account or redirected a recurring payment toward it, which is the intended behaviour. The other three were one legitimate payment, a bill the user had asked to pay "like last month", denied once in each of three attack runs, because the recipient does not appear in the task text. In Slack all 14 pairs finished, but only three tasks completed and the attack succeeded six times. Of 16 denied calls, nine carried the attacker's link to a colleague, but seven were messages the user's own task required, such as passing a summary of an article on to a colleague or posting a summary to another channel. Every successful Slack attack is the injection task whose goal is to visit a particular web address. That is a read-only web request, which the policy approves at a risk of zero because it never labels reads as unsafe, although the group's tool notes warn that a read can still carry data out through its address. In travel, 13 of the 14 pairs finished, three tasks completed and the attack succeeded once. All ten calls the policy denied were the attacker's hotel reservations, so no legitimate travel call was blocked, and the low completion there appears to come from the agent rather than the policy, although without the shared baseline this cannot be confirmed. The legitimate calls that were blocked have a shape the model had not seen: in the workspace suite a recipient is an email address that the task mentions, whereas in Slack it is a username and in banking a payee taken from the transaction history, so a legitimate send can look unrelated to the task and receive a high score. Without the shared approve-everything baseline we cannot say how much of the remaining loss in completed tasks is due to the policy and how much to the agent. The travel suite could not be completed in one pass, because the LM Studio server returned a server-side error on long conversations; running one pair at a time recovered 13 of the 14 pairs.

On the shared held-out splits, run once after the policy was frozen, the outcomes were identical at every budget, because the policy almost never escalated: of 114 decisions at a budget of two, only three were escalations, all in travel. In banking all 18 pairs finished, eight tasks completed and five attacks succeeded, so five pairs completed safely, a rate of 0.28. Every one of the five successful attacks was the injection task that changes the user's password; the policy approved the password change at a risk of 0.02 to 0.04, because its tool taxonomy treats it as an ordinary write, while it denied every attacker money transfer. Of its nine banking denials, six were the attacker's transfers and three were the user's own rent adjustment. In Slack all eight pairs finished, three tasks completed and no attack succeeded, with eight of ten denials aimed at the attacker's invitation and web posting and two at the user's own post of an article summary. In travel five of eight pairs finished, because three pairs hit the server error, two tasks completed and no attack succeeded. The three escalated travel calls were the attacker's calendar events, scored between 0.47 and 0.63, and the language-model reviewer denied all three with correct reasons, which is the first direct evidence in this work that escalating to a capable reviewer closes the gap seen in the workspace runs. With samples of eight to eighteen pairs these figures are indicative only.

The main limitations are as follows. The training data come from replayed ground truth, which is easier than a live agent, and the attacker sequences for eight of the injection tasks are our own assumptions. The classifier was trained on the workspace suite only. Real-run samples are small, at about ten pairs per setting in the workspace suite and 13 to 18 per suite elsewhere, with one injection task in the workspace runs, one attack template and one agent model. Of the 81 development traces collected on the hosted service, only 33 ran to completion because of rate limits and crashes, so real development data were scarce, at 70 safe and eight unsafe calls. Escalation was tested only against a reviewer that approves everything or against the same 20-billion-parameter model, not a stronger one. Several held-out workspace injection tasks could not run on the free tier at all. In the shared held-out run three travel pairs failed on the server error, and the run used a locally served agent with a 20-billion-parameter reviewer rather than the group's default settings.

## 5 Conclusion

A supervised classifier over context features is a cheap and, within one suite, effective approval policy. Offline it separated unsafe from safe calls almost perfectly, including for attack styles it had not seen, and in real runs it blocked every attack when it had to decide alone. Three lessons follow from the failures. Evidence from replayed data overstates real performance, because the labeling and leakage mistakes we found only appeared when we compared against an agent's own behaviour. A policy that escalates is only as safe as its reviewer, so the quality of the reviewer and the boundary between escalating and denying must be designed together. And a model trained on one suite transfers only partly: on other suites it still blocked the attacker's transfers, messages and reservations, but it missed an attack that arrives through a read-only tool and blocked some legitimate messages and payments whose arguments have a different shape.

The shared held-out run adds two further observations. The policy treats a password change as an ordinary write and approved every one, so a taxonomy built around sends and deletions needs to mark sensitive writes explicitly. And because it almost never escalated, the reviewer budget made no difference, so the escalation band is too narrow to use the reviewer well.

Several improvements follow directly. The model should be trained on ground truth from all four suites, using the shared tool metadata about whether a tool only reads, returns untrusted text or affects someone else, in place of name prefixes. A feature should check whether the address a read-only tool is asked to visit came from the user, so that a visit to an unmentioned address is flagged. The policy should be evaluated with a strong language-model reviewer, and the denial boundary re-tuned on development data. It could also be combined with a plan-consistency or provenance policy, which ask why a call is made rather than what it looks like. Finally, the real runs should be repeated with more tasks, more injection tasks and more seeds, so that differences can be tested statistically.
